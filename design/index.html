1 The big picture

Three crates, three jobs. The store knows nothing about sockets. The server knows nothing about storage. The leaderboard owns no state at all.

The whole system. One box per crate, arrows show who talks to whom.

Why three crates? So each part can be understood, tested, and changed alone. The store's tests never open a socket. The server's tests never touch a skip list. When something breaks, you know which box to open.

2 A request's journey

What happens, step by step, when a client sends SET score:sam 100.

One command, five steps. Steps 2–3 live in kv-server; step 4 lives in kv-core.

The tricky part is step 2: TCP delivers bytes in arbitrary chunks. A command might arrive in two pieces, or three commands might arrive in one piece. The parser handles both — it consumes complete frames and waits for more bytes when a frame is incomplete. That's the main thing task 001 teaches.

Pipelining: a client can send many commands without waiting for replies. The loop answers them in order. This is why Redis clients are fast — they batch.

3 Inside the store

One big map from keys to values — but a value can be three different shapes, and each shape exists for a reason.

Keys point at entries. An entry is one of three shapes, plus an optional expiry.

String task 001

The simplest shape: a key holds bytes. SET / GET / DEL, plus INCR for counters. Teaches the map itself.

Hash task 002

A key holds a mini-map of field → value. Player profiles, board metadata. Teaches the "one map, many value types" pattern.

Sorted set task 003

Members with scores, kept in order. This is the leaderboard. Teaches skip lists — the most interview-relevant structure here.

Expiry task 004

Every key can have a deadline. Lazy expiry on read + a background sweep for keys nobody touches. Seasonal boards are just expiring keys.

4 The skip list, zoomed in

The leaderboard needs "top 10" and "what rank is Sam?" to be fast with millions of players. A sorted array is too slow to insert into; a balanced tree is hard to get right. The skip list is the middle path Redis chose.

Each level is a linked list. Higher levels skip further. To find a score, start at the top and drop down — like an express train that stops less often.

Searching starts at the top level and moves right while the next score is too small, then drops a level. Each level roughly halves the search, so finding anything takes about log(n) steps. Inserting picks a random height for the new node — that's the whole trick, and it's why the code stays simple while a balanced tree needs rotations.

Paired with a hash map: the skip list answers "who's ranked where." A plain map from member → score answers "what's Sam's score?" in O(1). Together they cover every sorted-set command.

5 Concurrency: what is a Mutex<HashMap>?

The phrase that started this page. Here's the whole idea in one picture.

Three threads want the map. Only the one holding the lock touches it. The others wait.

A Mutex<HashMap> is a hash map with a lock wrapped around it. To use the map, a thread locks the mutex first; while one thread holds it, everyone else waits. Rust's twist: the mutex owns the map, so the compiler refuses to let you touch the data without holding the lock. Data races become compile errors instead of 3 AM production bugs.

But kvault barely needs it. The store runs on a single-threaded event loop, like Redis: one thread owns the map outright, commands run one at a time, and nothing can race. Mutexes only appear at the edges — the pub/sub subscriber list, shared metrics — where data is genuinely shared between tasks. If you see a mutex in the code, ask: "which threads share this, and why?"

Arc is the companion: a shared, reference-counted pointer that lets multiple threads own the same mutex. Arc<Mutex<T>> is Rust's standard "shared mutable state" idiom — you'll see it everywhere, and now you know what it says: many owners, one at a time inside.

6 Full-duplex & pub/sub

"Duplex" just means both directions at once. A TCP connection can carry requests one way and replies the other, simultaneously and independently.

Top: full-duplex — requests and replies flow independently. Bottom: pub/sub — one publish fans out to every subscriber.

Tokio expresses this by splitting a socket into a read half and a write half, each owned by different code. Most commands don't need the split — the loop reads, then writes, in order. Pub/sub is where it matters: a subscribed connection must receive messages at any moment, even while idle, so one task owns the read half (listening for UNSUBSCRIBE) while another owns the write half (pushing messages). That's also exactly how the leaderboard's live WebSocket works: score lands → publish → every watching dashboard gets pushed the update.

7 Persistence: memory is fast and forgetful

Everything so far lives in RAM. Restart the server and it's gone. Two mechanisms fix that, the same two Redis uses.

The diary records every change; the photo is a shortcut so restarts don't replay years of diary.

The tradeoff: writing the diary on every command is safest but costs a disk write per command. Redis's default is once a second — you might lose a second of writes in a crash, and that's usually fine. Which policy kvault uses is an open decision (§11 in the design doc).

8 The leaderboard: the store, with a point

The service owns no state — every read and write goes to the store. That constraint is what makes it a good demo of the store.

Submit a score → it lands in a sorted set → an event fans out → every open dashboard updates live.

Seasons work the same way: a board is just a key, and a key can expire. When a season ends, the old board's key gets a TTL and a new season starts under a fresh key. No cleanup code — expiry does it.

10 Rust primer — just enough for kvault

You've never used Rust. These seven ideas are all you need to read this codebase. Full version in the repo: docs/rust-primer.md.

1. Ownership & borrowing

Every value has one owner; when the owner goes away, the value is freed. You can borrow references, but the compiler enforces: many readers or one writer, never both.

Where: everywhere. Most compile errors are this rule, and they're usually right.

2. Option & Result

No null, no exceptions. Option is Some/None (a value that might be absent). Result is Ok/Err. ? propagates errors up. The compiler makes you handle both cases.

Where: GET on a missing key → None; I/O → Result.

3. Structs, enums, match

Enums can carry data — the store's Value is String, Hash, or SortedSet. match forces you to handle every variant, so adding a type breaks the build until all handlers are updated.

Where: kv-core's value types, the RESP parser.

4. Traits

A trait is a set of methods a type promises — like an interface. Rust's polymorphism without inheritance.

Where: shared behavior, e.g. a persistence-backend trait.

5. Arc & Mutex

Arc: many owners of the same data. Mutex: a lock — one thread inside at a time, and the compiler enforces it. Together: shared mutable state, safely.

Where: pub/sub registry, metrics. Not the hot path (§5).

6. async / await & Tokio

Tasks that pause while waiting instead of blocking a thread. One thread juggles thousands of connections because most are idle. .await is where a task can pause.

Where: one task per connection in kv-server.

7. Modules, crates, Cargo

A crate is a library or binary; a workspace groups crates. Cargo.toml declares dependencies. Everything is private unless marked pub.

Where: three crates, one workspace, one cargo build.

Reading Rust

:: separates paths. ! means a macro (println!). & borrows. /// comments document public items — read those first.

Where: every file. When stuck, read the error — Rust's are famously helpful.

12 Glossary

TermPlain meaning
RESPRedis's wire protocol — the byte format clients and servers speak. Five types: simple strings, errors, integers, bulk strings, arrays.
Event loopOne thread that waits for I/O events and handles them one at a time. No thread per connection — that's how one thread serves thousands of clients.
Full-duplexBoth directions of a connection usable at the same time (§6).
MutexA lock: one thread at a time touches the data (§5).
ArcA shared pointer; many threads can own the same data, freed when the last owner drops it.
Skip listA layered linked list with O(log n) insert, lookup, and rank (§4).
AOFAppend-only log of write commands, replayed on startup (§7).
PipeliningA client sending many commands without waiting for replies.
p50 / p99The latency 50% / 99% of requests beat. p99 is the "how slow does it feel when it's slow" number.
ShardA slice of the data, owned by one loop/thread. Sharding splits work across cores.
